# E-Hentai 全画廊媒体预加载优化设计

## 目标

在不牺牲 E-Hentai/H@H 稳定性的前提下，提高整本画廊的后台图片预加载速度。完整画廊应继续由网关生成连续阅读页面，图片下载由网关缓存和预加载队列完成，客户端无需增加任何配置或订阅步骤。

## 当前证据

- 143 页画廊的详情 HTML 已能在公网约 5 秒内生成，页面显示 `143 / 143`，说明详情页并发解析不是主要瓶颈。
- 首尾图片通过网关均返回 HTTP 200，单张耗时约 0.7–3 秒，主要耗时来自 H@H 媒体节点。
- 当前详情页预取并发为 8，媒体后台预热并发为 3；缓存目录已持久化并限制为 5GB，媒体缓存 TTL 为 7 天。

## 设计方案

### 自适应媒体预热队列

将固定并发的媒体预热队列改为带反馈的有限 worker 池：

- 初始并发为 4；
- 连续成功且没有限流/超时信号时逐步提升，最高 6；
- 出现 429、408、425、5xx 或传输超时时降低并发，最低 2；
- 失败任务使用有上限的指数退避和抖动重试，避免同时重试造成雪崩；
- 每个媒体源 origin 单独统计成功和失败，单个 H@H 节点异常只影响该节点，不阻塞全局队列；
- 队列去重，并复用缓存层的同 URL in-flight 合并。

### 缓存与一致性

- 保留现有 5GB 持久化缓存和 7 天媒体 TTL；
- 预热命中缓存时不访问上游；
- 图片下载失败时允许读取未过期或可安全复用的旧媒体缓存；
- 不缓存带 Range 的视频请求，不改变现有视频拖动行为；
- 不延长 E-Hentai `/s/` 图片详情 HTML 的短 TTL，避免复用过期 keystamp。

### 可观测性

记录不包含 token、完整源 URL 或凭据的聚合事件：

- 预热任务入队、命中、下载成功、重试、最终失败；
- 当前并发、成功率和退避原因；
- 按 hostname 记录结果，hostname 只用于诊断，不写入用户内容。

## 非目标

- 不修改 RSSHub 源码或 RSSHub 原生 token 逻辑；
- 不引入独立数据库、消息队列或新的客户端操作；
- 不通过无限并发绕过 H@H 的服务限制；
- 不改变阅读器的连续阅读 HTML 结构和图片顺序。

## 测试策略

先增加失败测试覆盖：

1. 成功反馈会逐步提升并发但不超过上限；
2. 限流/超时反馈会降低并发并执行有限退避；
3. 不同 origin 的失败不会阻塞其他 origin；
4. 重复 URL 只产生一个预热任务；
5. 现有完整画廊仍保持 143/143、无尾部误报，并且媒体地址可返回 HTTP 200。

完成后运行完整 `npm test`，从正确的生产 Compose 目录重建，再验证 `/readyz`、完整画廊摘要、首尾媒体请求和容器稳定运行状态。

## 回滚

若上游错误率升高，先将媒体预热并发恢复为 3 并重新构建；若仍异常，可暂时停用后台媒体预热，客户端按需读取现有缓存和上游媒体，详情页解析功能保持不变。
