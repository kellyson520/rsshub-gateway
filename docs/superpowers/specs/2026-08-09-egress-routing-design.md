# 网关分流与多出口底座设计

## 目标

将网关外部请求按领域策略分为公共出口和固定出口：E-Hentai 公开排行、公开漫画详情、公开图片媒体使用公共出口池；ExHentai 与需要登录的站点使用固定出口。多出口池作为所有站点模块共享的底层基座，每个健康 Mihomo 实际代理节点最低 3 路并发，按运行结果自适应扩容到默认 6 路，并保留 E-Hentai 预热的缓存、失败退避和恢复能力。

## DDD 边界

- 领域层 `egress-policy`：只判断目标属于 `public` 还是 `sticky`，不依赖 Mihomo、HTTP 或 Docker。
- 应用层 `upstream`：为外部请求附加分流策略诊断，并保持现有重试、熔断和来源 Header 行为。
- 基础设施层 Mihomo：通过 `PUBLIC` 节点发现、`EGRESS_LANE_01..12` 固定 listener 和 `STICKY` 稳定组执行出口选择。
- 共享传输层 `upstream`：所有站点模块只调用 `fetchExternal`，统一处理 allowlist、超时、重试、熔断、出口租约和响应体结束后的释放。
- 预热上下文：独立管理 E-Hentai 图片缓存、任务持久化和源级公平性，实际网络并发由共享出口池限制。

## 分流规则

公共组：

- `e-hentai.org` 的 toplist、gallery、image 页面；
- `ehgt.org` 缩略图与公开媒体；
- `*.hath.network` 图片媒体。

固定组：

- `exhentai.org` 及其子域；
- X、Twitter、Instagram、Iwara、Telegram、Telesco.pe 及其媒体域；
- 未明确列为公共内容的其他外部目标。

公共组使用健康节点对应的 lane 轮询；每个 lane 初始 3 路，连续成功后逐步升档，遇到 408/425/429、5xx 或超时降档但不低于 3 路。固定组使用单一健康出口，健康检查失败时才重新选择节点。RSSHub 容器内网请求不经过该分流层。

## 并发与稳定性

- 每个健康代理节点最低 3 路，默认最高 6 路；最多启用 12 个节点，全局预热上限 48 路；
- 单 H@H origin 同时最多 2 个请求；
- 429、408、425、5xx 和超时触发降速及有限重试；
- 公共组节点故障只影响当前请求，固定组不因普通公共媒体失败而换出口；
- 5GB 媒体缓存、7 天 TTL 和队列持久化保持不变。

## 验收

- 领域测试准确区分 E-Hentai 公共/ExHentai 固定/登录站点固定/未知目标固定；
- Mihomo 配置通过 `mihomo -t`；
- 每个健康出口最低 3 路、动态升降档和租约释放测试通过；
- 143 页画廊仍为 143/143、无误报；
- 公共和固定请求均能通过网关，容器无重启，readyz 正常。
